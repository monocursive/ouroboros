## Refusal status and live boundary tests

The initial complete optimized Linux rerun passed: **1,727 passed, zero
failed, 16 ignored** ([summary](results/linux-followup/before-exit-fix/summary.json),
[log](results/linux-followup/before-exit-fix/test.log)). A new live regression
then found that replacing a pinned backend correctly prevented execution but
returned exit 1. The specification requires exit 125 for refusal before exec.
The [failing test output](results/linux-followup/before-exit-fix/boundary.log)
is retained.

The shared refusal handler now returns 125 for `internal_error` before exec.
A running tool failure still returns 1. The new portable regression covers
that distinction. Three deterministic Linux tests exercise:

- Backend replacement and permission changes after pinning. Both refuse at
  `preparing`, with `internal_error`, exit 125 and no target side effect.
- Execution through the pinned descriptor after the pathname is replaced.
  The original image executes and the backend descriptor is closed in it.
- Creation of a nested `.git` after scanning, without replacing its parent
  inode. Revalidation refuses before the target runs.

The [focused optimized boundary suite](results/linux-followup/boundary.log)
passed **26/26** after the fix. It uses
a private forwarding executable for the installed bubblewrap; the test does
not modify the distribution backend or its AppArmor configuration.

This proves the final handoff revalidation cases. It does not close K07's
separate requirement to force two consecutive changes during the scan, nor
the documented external-writer window after the final check.

## K17 measurement method

Before this follow-up measurement, K17 was made explicit: twice J5's retained
phase budgets means **under 500 ms p95 added startup** for every workload and
**at most 100% median post-start overhead** for file operations, observation
off versus direct execution, on `tool`. This replaces the ambiguous use of
whole-invocation timings as a startup budget. Observation-on costs remain
separate measurements.

The [recorded command](results/linux-followup/perf-run.sh) uses `xtask perf` with five warmups and 30 measured
launches per arm, direct/off/on, plain and delegated sessions, no-op,
200 children and 5,000 file-operation rounds. The predeclared one-minute load
limit is **3.0** on the four-CPU host, the same threshold as the archived J5
run. No excluded samples or loaded comparisons can receive a passing K17
verdict.

The [K17 checker](performance.py) consumes a summary recomputed from the raw
launch records; its [eight regression tests](test_performance.py) cover
missing/duplicate cells, insufficient or excluded samples, host load, fixture
changes, integrity and budget boundaries. They pass on the Mac and are included
in the contracts workflow. This local result does not claim a hosted CI run.

## K17 results

**Pass:** 630 launches recorded, comprising 90 warmups and **540 valid measured
launches**, with **zero exclusions**. Measured one-minute host load ranged from
0.83 to 1.63 (median 1.22), below the declared 3.0 limit. The raw-data integrity
check passed. The [summary](results/linux-followup/perf/summary.json) was
recomputed from the [raw launches](results/linux-followup/perf/launches.ndjson)
on Linux and independently on the Mac; every field matches except the
recomputation timestamp ([comparison](results/linux-followup/macos-recompute.json)).
The [K17 verdict](results/linux-followup/k17.json) binds to the summary SHA-256.

Added startup is the target-entry time minus the direct arm's median startup,
reported at p95. Post-start includes work and teardown; its overhead is the
ratio of medians minus one. Only the fixed file workload has a post-start budget.

| Session / workload | J5 added startup p95 ms | New added startup p95 ms | New file post-start overhead |
|---|---:|---:|---:|
| Plain / no-op | 122.1 | 123.4 | — |
| Plain / 200 children | 118.9 | 124.0 | — |
| Plain / 5,000 file rounds | 128.1 | 130.6 | 36.6% |
| Delegated / no-op | 109.0 | 123.9 | — |
| Delegated / 200 children | 101.3 | 108.6 | — |
| Delegated / 5,000 file rounds | 109.1 | 120.8 | 40.1% |

The [archived J5 run](../../specs/jail-v1/evidence/perf-2026-09-25-ouro-ci/summary.json)
recorded 39.5% / 40.3% file post-start overhead. These are separate runs on the
same host, not paired estimates of a code change. The new run also meets J5's
retained 250 ms / 50% ceilings. The Rust summary retains the original 20%
comparison fields, which still fail for file operations; those are not K17's
declared thresholds.

All **60 observation-off no-op samples** carry `exec_unconfirmed`, exit 1:
the target's own timing report proves the work ran, but the jail could not
independently confirm the short-lived exec. J5's explicit flagged-sample rule
allows those timing measurements. They are not successful-execution receipts.
Every other measured jailed launch has a successful settled outcome. All
180 observed launches have exact expected event counts, verified tree death,
complete traces and no coverage/observer loss.

Observation adds **41.9%–44.0% median post-start time** on the 200-child
fixture, and **301.9%–305.9%** on the file fixture (about 4.0–4.1 times the
observation-off post-start time). Full file-workload wall timings are:

| Session | Direct median / p95 ms | Observation off median / p95 ms | Observation on median / p95 ms |
|---|---:|---:|---:|
| Plain | 189.9 / 262.9 | 375.2 / 440.2 | 1,166.8 / 1,283.1 |
| Delegated | 185.0 / 212.9 | 362.0 / 409.0 | 1,136.6 / 1,210.7 |

The no-op's shorter observed teardown comes with independent exec confirmation;
it is not evidence that observation accelerates useful work. This Linux phase
measurement does not turn the Mac's refusal timings into a containment result.
